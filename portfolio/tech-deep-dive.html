01. fcoach — 경기 데이터에서 실행 가능한 코칭까지

개인 프로젝트. Nexon Open API·FC Online DataCenter의 경기 데이터를 수집·정규화하고, 분석 결과를 팀·선수·경기 리포트, 랭커 비교 및 맞춤 코칭으로 이어지는 웹 서비스로 구현했습니다. LLM 서비스가 아니라 규칙·지표 기반 데이터 분석 서비스입니다.

문제 정의와 최신 서비스 흐름

단순 전적 조회는 승률 등 결과 지표를 보여주지만, 사용자가 어떤 플레이를 조정하고 무엇으로 검증할지까지 연결하기 어렵습니다. 이를 분석→원인 확인→행동 제안→변화 확인의 흐름으로 구성했습니다.

감독명/OUID 조회경기 데이터 수집·정규화팀·선수·경기 KPI랭커/상대 비교맞춤 코칭·최근 경기 추이

최신 버전은 공개 스쿼드 피드 연결(선택), 포메이션에서 같은 포지션 선수 교체 비교, 슈팅 위치·유형 필터, 선수 2인 비교, 랭커 분포와의 차이 등도 제공합니다. 피드 정보는 저장된 설정으로, 그 설정이 과거 경기에서 실제로 적용됐거나 발동했다는 사실을 증명하지는 않습니다.

왜 이 구조로 설계했는가

  • 외부 API와 분석 API를 분리: API 응답 형식과 데이터 누락 조건을 정규화 계층에서 다루고, 화면은 계산된 KPI와 설명을 받도록 구성했습니다.
  • 읽기와 동기화 경로 분리: 이미 받은 경기 기록은 재사용하고 새 경기만 조회해 불필요한 호출을 줄이도록 설계했습니다.
  • 호출 제한과 병렬 처리: 경기 상세 조회는 요청당 4개, 프로세스 전체 8개 작업자 범위로 제한합니다. 이는 설정된 동시성 한도이며, 실제 지연시간 개선율을 측정한 수치는 아닙니다.
  • 운영 현실과 저장소 선택: 초기에는 SQLite 스냅샷 저장 구조를 사용했습니다. 단, Vercel serverless 인스턴스의 로컬 SQLite는 영구 저장을 보장하지 않으므로 장기 추적에는 관리형 데이터베이스가 필요합니다. Redis 캐시·락은 선택 구성입니다.

운영 통계: 수치보다 먼저 측정 정의

2026년 10월 23일 이후 계측 정의를 개선했습니다. 신규/재방문, 페이지뷰, 공개 피드 목록·선택·분석 연결, 전후 비교 완료·실패 등을 구별하고, 이벤트 실행 횟수와 익명 브라우저 수를 혼동하지 않도록 정의했습니다.

이전 포트폴리오의 adopt_action·view_evaluation은 과거 실험 API 이벤트입니다. 최신 전후 비교 기능은 before_after_completed 등 별도 이벤트로 계측하며, 이전 지표를 현재 기능 이용량에 합산할 수 없습니다.

성과·한계 및 개인 기여

개인 구현: API 연동, 정규화, KPI·랭커 비교 기준, FastAPI·Next.js 화면, 이벤트 계측과 배포. 실제 동작하는 서비스와 코드로 검증 가능합니다. 한계: 운영 데이터의 지속 저장, 중복 방문 및 기간별 계측 기준 변경, 외부 데이터의 제한·결측을 고려해야 합니다. 전후 지표 변화가 코칭 조언의 인과 효과를 증명하는 것은 아닙니다.

02. RMSE — 자연어 의도를 검색 가능한 추천으로

부스트캠프 AI Tech 8기 최종 5인 팀 프로젝트. 자연어 상품 요청을 구조화하고, 후보 생성과 ML 리랭킹, LLM 설명을 결합했습니다. 본인의 기여 범위는 Electronics EDA, 추천 아키텍처 설계, 프롬프트 흐름 설계입니다. 팀 전체 코드 구현을 개인 단독 작업으로 기재하지 않습니다.

문제와 설계 선택

“여행에서 브이로그용으로 쓸 가벼운 카메라”처럼 목적·상황·제약이 섞인 입력은 키워드 일치만으로 검색하기 어렵습니다. 또한 단일 LLM에게 상품을 바로 고르게 하면 실제 카탈로그에 없는 제품이나 검증되지 않은 추천 근거가 생성될 수 있습니다.

자연어·대화 맥락LLM 의도·스펙 추출카테고리/facet 필터Two-Tower 벡터 검색CatBoost 리랭킹후보 근거 기반 LLM 설명
  • LLM API를 쓰는 이유: 다양한 자연어 표현을 검색 조건과 후속 대화 상태로 변환하고, 실제 후보 아이템의 속성을 사용자의 목적에 맞게 설명하는 역할을 맡깁니다.
  • 검색·리랭킹을 분리하는 이유: 전체 카탈로그에서 후보를 빠르게 줄이는 단계와 그 후보의 다차원 피처를 평가하는 단계를 별도로 최적화하기 위해서입니다.
  • Two-Tower를 고려한 이유: 쿼리와 상품을 각각 임베딩해 후보 검색에 활용할 수 있습니다. 속성별 입력 구성과 통합 표현 간의 선택 기준, 실제 모델 비교 수치는 실험 노트 확인 후 구체화할 항목입니다.
  • LLM 설명의 위험 통제: 서비스 구조상 리랭킹된 실제 후보 목록을 응답 생성 단계에 전달합니다. 다만 설명의 사실 일치율을 측정한 결과가 확보된 것은 아닙니다.

서비스 코드로 확인한 계약·상태 관리

Decision 서비스는 사용자 대화와 llm_state/session_state를 전달하고, 추천 요청이 감지되면 user_query·query_category로 검색기를 호출합니다. 반환된 후보 아이템을 LLM 서비스에 다시 전달해 설명을 생성하도록 구성돼 있습니다.

llm_state/session_state는 JSON 문자열일 경우 객체로 정규화하고, Redis에서 세션 상태를 불러오고 갱신합니다. 이 방식은 모듈 경계를 명확하게 하지만 서비스 간 왕복 지연과 상태 불일치, 오류 시 롤백 문제를 남깁니다. 실제 코드에도 실패 시 상태 롤백/재시도 전략이 후속 과제로 표시돼 있습니다.

GPT API 모델명과 선택 근거 — 확인 범위

프로젝트 README는 HyperCLOVA X와 OpenAI API를 함께 활용했다고 명시합니다. 다만 확인한 develop/service/decision 코드에서는 별도의 LLM API 서비스를 호출할 뿐, 실제 OpenAI 모델 ID·스냅샷이나 호출별 비용·응답시간이 고정돼 있지 않습니다. 따라서 GPT-4o, GPT-4o-mini 등 구체적인 모델을 임의로 적지 않습니다.

추가 확인 필요: LLM 모듈의 실제 model 파라미터, 프롬프트 버전, HyperCLOVA X/OpenAI 역할 분담, 모델 선택 당시의 품질·비용·지연 비교 기록. 이 기록을 확보하면 “왜 이 버전을 사용했는지”를 사실 기반으로 확장할 수 있습니다.

정량 근거와 한계

데이터 규모(리뷰·메타데이터)는 프로젝트 README에서 확인됩니다. 반면 온라인 CTR, 추천 성공률, 단계별 지연시간, LLM 의도 해석 정확도 등은 검증 가능한 최종 값이 없으므로 기재하지 않았습니다. 다음 단계에서는 검색 후보 Recall@K, 리랭킹 성능, 검색 조건 추출 유효율, 근거 없는 설명 비율, 응답시간·토큰 비용을 각각 측정하는 것이 타당합니다.

왜 단순 GPT 챗봇이 아닌 2-Stage인가

사용자 발화에 곧바로 한 문장으로 답하는 방식만으로는 감정 파악, 상담 관점 선택, 세션 맥락 유지와 일관된 응답 전략을 제어하기 어렵습니다. 프로젝트는 Supervisor가 상담 접근법과 가이드를 선택하고 Counselor가 사용자에게 전달할 응답을 생성하도록 역할을 나눴습니다.

사용자 발화·대화 이력Insight 추출Supervisor 전략 선택CBT/ACT/DBT 등 가이드Counselor 응답상태·로그 저장

코드에는 세션 단위 Fixed 방식과 대화 맥락에 따라 전략을 변경하는 Dynamic 방식, 프롬프트 결합형 Ensemble을 비교한 흔적이 있습니다. 상담 기법 선택과 실제 표현 생성을 분리하면 전략을 비교·수정하기 수월하지만, 모델 호출 횟수 증가와 오류 전파라는 비용도 발생합니다.

실제 모델 ID와 파라미터

model/chat.py, model/mascc.py, model/agents/utils/args.py에서 기본 모델 ID gpt-4o-mini를 확인했습니다. 이는 날짜가 고정된 모델 스냅샷 ID가 아닌 모델 별칭입니다. 당시 정확한 백엔드 스냅샷을 별도로 고정했다는 증거는 없습니다.

GPT-4o mini는 2024년 공개 당시 낮은 호출 비용과 지연시간을 고려한 소형 모델로 소개됐으며, 128K 컨텍스트와 최대 16K 출력 토큰을 지원했습니다. 상담 파이프라인처럼 여러 번 LLM API를 호출하는 구조와 기술적으로 맞는 특징입니다. 다만 이것이 팀이 실제 선택 당시 기록한 이유인지, GPT-4o 등과 비용·품질을 비교했는지는 확인되지 않았습니다.

평가: 팀의 관측 결과와 해석 범위

팀의 모델 README에 따르면 450개 페르소나·시나리오 기반 대화를 생성해 CTRS 6개 항목을 LLM으로 평가했습니다. Fixed Supervisor 구성이 6개 중 5개 항목에서 가장 높은 평균을 기록했고, README에는 베이스라인 대비 평균 약 19.25% 개선으로 기술돼 있습니다.

별도의 A/B 테스트는 실제 사용자 83명을 대상으로 Fixed(A)와 Dynamic(B)를 비교했습니다. 팀 문서는 Dynamic(B)의 공감도·응답 적절성·상담 만족도가 더 높았다고 보고합니다. 두 결과는 평가 방식이 다르므로 모순으로 단정하거나 단일 성능 수치로 합산할 수 없습니다.

React 프론트엔드, Spring Boot API 서버, FastAPI 모델 서버, PostgreSQL 데이터 저장 계층을 연동하고, 각 서비스를 Docker로 패키징해 GCP Cloud Run/Cloud SQL에 배포하는 팀 구조를 사용했습니다. 본인은 PM·주요 화면 구현과 상담 대화 흐름의 요구사항 구조화, 커뮤니티 사용자 경험 설계에 참여했습니다.

보강할 점: 상담 서비스 안전 정책, 자해·위기 발화 대응 프로토콜, 프롬프트 버전 관리, 모델 비용·지연 측정과 장애 시 폴백을 분리해 검증해야 합니다. 또한 모델 선택 당시의 대안 비교표가 확인되지 않아 선택 이유를 추측해 확정적으로 쓰지 않았습니다.
